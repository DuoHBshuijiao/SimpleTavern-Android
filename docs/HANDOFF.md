## 1. 项目初衷

- 作者 Milton 自用，角色和世界观基本都是自己原创，不依赖社区角色卡。
- 原来用 JanitorAI，图的是多端云同步。离开的原因：Janitor 用旧 tokenizer 高估 token，实际七八万就当作 128K 截断；截断方式是滚动窗口，API 缓存命中不了；每几十句就得手动总结、开新会话。
- 没有转向 SillyTavern，原因：设置被拆得很碎，看不出是否已保存；添加 API 时参数一大堆，不知道哪些必填，"测试"按钮总报错；世界书、正则等对原创玩法是负担；安卓上要靠 termux。
- 所以自己做：比纯 chatbot 多出角色管理和记忆，其他功能"好用就行"。先写了桌面端（`SimpleTavern-Desktop`：Vue 3 + FastAPI + JSON），边写边玩，前后四五个月。

## 2. 现在的定位

- **手机是主力。** 作者现在不爱在电脑上聊，出差时也全靠手机。桌面端退居二线。
- **同步暂不做。** 需要做的是把桌面数据一次性完整迁移到手机，之后以手机为准。
- 上下文由作者手动管理，他从不开自动总结或自动上下文管理。桌面端已支持滚动截断和分段截断两种模式（可切换），并配有作者自己写的上下文成本计算器（动态规划，考虑了缓存价格）。
- 缓存命中率**有意**只做全会话汇总，不需要逐轮明细或导出。

## 3. 功能取舍（决定安卓 UI 露出什么）

| 级别 | 功能 |

## 4. 安卓工程现状

- `core/*` 8 个模块、`runtime/*` 2 个模块，由 Codex 照着桌面端逻辑用 Kotlin 复刻。作者本人没有看过这部分代码。只验证过能编译，真机和真实上游都没验收。
- `app` 只是诊断宿主（3 个文件），**尚无 Compose UI 依赖，已声明 Kotlin 2.0.21 Compose 编译插件**。compileSdk/targetSdk 35，minSdk 26，Kotlin 2.0.21，AGP 8.7.3。
- 入口：`SimpleTavernCore.get(context)`，是一个单例门面。没有使用 DI 框架。
- 流式：`observeGeneration(chatId)`，重放最近 256 条事件的 SharedFlow（新生成清空旧窗口），正文每 500ms 落一次库。UI 以数据库为准，收到 `Done` 后刷新。
- 接口说明见 `docs/android/CORE_API.md`。**下面列出的签名只对过文档，还没对照源码核实。**

## 5. 后端问题历史记录（2026-10-29 修复状态见文首链接）

按优先级：

1. **token 估算疑似使用 chars/4**（出自 `docs/android/CHAT.md`，源码未核实）。中文约 1 字 ≈ 1 token，这样会低估 3–4 倍，作者的上下文计算会因此失真。建议改用真正的 BPE，可以复用桌面的 DeepSeek `tokenizer.json`，并扣除 `max_tokens` 和注入块。
2. **核实分段截断模式是否已从桌面复刻。** 桌面的两种截断模式可以切换，安卓文档里只看到"消息条数 50% 回落阶梯"加上按 token 的滚动裁剪。
3. `context_size=0` 时不做任何裁剪；没有设消息条数上限时会读取全部历史（`STATUS.md` 已承认）。
4. Gemini 遇到 404 或缓存失效直接失败，不会重建（桌面会重建一次）。另外，history_tail 在滚动截断下可能每轮都新建 cachedContents。
5. OpenAI 的 explicit 缓存模式在旧模型或 Chat 接口上直接报 Unsupported，桌面是自动降级。
6. **前端需要、但后端缺失的接口：**
   - 消息、会话、角色、Persona 列表的可观察 Flow
   - "正在生成"状态的 StateFlow
   - 有类型的设置模型（目前 `getSettingsJson` 只返回原始 JSON）
   - 预设"测试连接"
   - 公开的 Preset、MessageCandidate、StreamEvent、StError 结构定义；思考、工具调用、缓存命中是否有独立的流式事件
7. 数据迁移：桌面的 `backup_settings` ZIP 不包含聊天图片、工作区、用量记录（见 `DATA_MODEL.md` 88–90 行）。正式搬家前要确认导出是否完整。

已被作者否定的结论，**不要再提**：
- "两端都只有滚动窗口，重现了 Janitor 的问题"：桌面支持分段截断。
- "总结和截断脱钩是高危问题"：作者不用自动总结。
- "命中率应该按会话、按轮次细化"：汇总是有意的设计。

## 6. 前端设计方向（已定）

- 视觉锚点是**扑克牌**，风格是华丽的装饰风，不走科幻触感。底色以黑白为主，主题色只用在少数地方，偏好衬线字体，**不要聊天气泡**。
- 操作要像游戏一样有"演出感"，可参考 Persona、全境封锁、死亡空间的 UI。作者大概率是唯一用户，可以为体验牺牲"秒开即用"。效果的性能成本不是问题。
- **首页是牌架**：左右滑选角色，上下滑选会话；镜头倾斜、镜像，方便右手拇指沿 45–60° 方向滑动；有边界，缺的位置放空白占位牌。
- **会话就是一副牌**：选中后以弹簧动作从牌架里抽出，悬停在画面中央、纵向铺满。中间一张牌正对镜头，显示最新回复预览，上下各有两张逐级倾斜的牌；上下滑预览历史，点击进入全屏。
- **牌组纵列从上到下**：旧历史的薄牌边、两张弯折牌、正面大牌、一张背面朝上的牌（抽它就是写新消息）、薄牌边，最底部两个 tab：menu 和 setting。
- **写新消息**：像赌场里看底牌那样，手指捏住牌背近端，把牌卷起来朝向镜头，不是对折。全屏编辑时整张牌被拿起，当前正文向上收起。
- **设置**：一段洗牌动画（riffle 或 cascade）盖住屏幕，然后翻开一张牌，牌面就是设置页。
- **其他已定交互**：
  - ＋ 是半屏面板，记忆设置放在里面。
  - 新会话的准备方式：角色、用户身份、情景三个圆角按钮各自展开成列表，下面是"新建会话"按钮。
  - 历史列表：用柔光表示新近程度（暖橙 = 2–3 天内，蓝灰 = 3–7 天，无光 = 更早），左侧用角色主题色的线把同一系列串起来；标题不加副标题，也不需要图例。
  - 群聊里玩家固定扮演一个角色。
- 牌组原型已经可以作为参考，作者知道接下来要做成什么样。
